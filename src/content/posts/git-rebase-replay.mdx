## The one idea

{/* THE sentence: a commit's identity is its hash, and the hash is computed from its
    content AND its parent. Change the parent and you don't move the commit — you
    compute a WHOLE DIFFERENT commit. So rebase can't move anything; it re-creates. */}

## What rebase actually does, step by step

{/* Intent: feature has B, C off an old base; main moved to Y. Rebase: read the CHANGES
    B introduced → write a new commit B' with those changes but parent = Y → read C's
    changes → write C' on top of B' → point feature at C'. Old B, C untouched, now
    orphaned in the object store. Linear, clean history is the OUTPUT; new objects are
    the mechanism. */}

{/* <RebaseReplay /> — interactive: show B,C on old base + moved main. Hit "rebase" and
    watch B',C' get WRITTEN as new nodes (new hashes) on top of main, the branch pointer
    hop over, and the original B,C fade to orphaned. The new-hash reveal is the payoff.
    Build when writing. */}

## Why "never rebase shared history"

{/* Intent: the practical rule, now obvious rather than memorized. If a colleague has the
    OLD B,C and you replace them with new-hash B',C', Git sees two unrelated sets of commits
    with the same changes → duplicate commits, conflict soup on the next merge. Safe on
    local un-pushed branches; dangerous on anything others have pulled. Contrast with
    [[git-merge-ff-vs-3way]]: merge preserves the true (messy) history, rebase rewrites a
    clean (fictional) one — a trade, not a right answer. */}
